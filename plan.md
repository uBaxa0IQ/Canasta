# Канаста Online — план разработки

Стек: **FastAPI (backend) + React (frontend)**, WebSocket для realtime, Redis для активного состояния партий, Postgres для персистентной истории. Весь стек (backend, frontend, Postgres, Redis) поднимается через Docker Compose — для разработки и для продакшена отдельные конфиги (раздел 18, шаги 2.1 и 31).

---

## 1. Роли пользователей

Полноценной регистрации на старте нет — вход по имени + ссылке, минимум трения.

- **Гость/Игрок** — базовая роль, есть у всех
- **Хост лобби** — создатель комнаты, доп. права управления (кикнуть, рассадить, начать игру, задать настройки)
- *(опционально, не MVP)* **Наблюдатель** — зритель без права хода

---

## 2. Настройки лобби (правила — конфигурируемые)

Хост задаёт параметры при создании комнаты, до старта партии их менять нельзя.

| Параметр | Варианты | По умолчанию |
|---|---|---|
| Целевой счёт партии | 3000 / 5000 / кастом | 5000 |
| Видимость стопки сброса | вся стопка видна всем / только верхняя карта | только верхняя |
| *(задел на будущее)* Пороги первого выхода | стандартная таблица / кастомная | стандартная |
| *(задел на будущее)* Количество колод | 2 колоды (108 карт, стандарт) | 2 колоды |

Остальные правила (кража козыря, состав канаст, штрафы) в MVP фиксированные — не выносим в настройки, чтобы не взрывать сложность движка сразу. Помечено как "задел" то, что можно добавить вторым заходом, если появится спрос.

## 3. Функциональные требования

### 3.1 Управление лобби
- FR-1: Пользователь может создать комнату, указав имя и настройки (см. п.2)
- FR-2: Система генерирует уникальную короткую ссылку-приглашение
- FR-3: Пользователь может войти в комнату по ссылке/коду, указав имя
- FR-4: Хост распределяет игроков по 4 местам (2 команды по 2, партнёры друг напротив друга)
- FR-5: Хост может кикнуть игрока до старта партии
- FR-6: Хост может запустить партию, когда все 4 места заняты
- FR-7: Игрок может переподключиться к своей партии после разрыва соединения/перезагрузки страницы

### 3.2 Игровой процесс — раздача и стол
- FR-8: Система раздаёт каждому игроку 13 карт при начале сдачи
- FR-9: Система отображает игроку его руку, скрывая карты остальных
- FR-10: Система отображает общий стол: колоду (счётчик), стопку сброса (вся или верхняя карта — по настройке лобби), мельды обеих команд
- FR-11: Система отображает текущий счёт обеих команд и текущий порог первого выхода для каждой команды

### 3.3 Ход игрока
- FR-12: В свой ход игрок может взять карту из колоды
- FR-13: В свой ход игрок может забрать всю стопку сброса (если не заблокировано тройкой сверху)
- FR-14: После взятия сброса система требует выложить минимум одну новую комбинацию в этот же ход
- FR-15: Игрок может выложить новую комбинацию (набор или последовательность) из карт руки
- FR-16: Игрок может доложить карты в существующую (незакрытую) комбинацию своей команды
- FR-17: Игрок может украсть козырь из комбинации противника, положив взамен нужную натуральную карту
- FR-18: Игрок может сбросить одну карту, завершая ход
- FR-19: Игрок может завершить сдачу (выход), если у команды есть хотя бы одна завершённая канаста и рука пуста

### 3.4 Первый выход и накопление порога (несколько комбинаций за ход)
Порог открытия — это **сумма очков всех новых комбинаций, выложенных командой за этот ход**, а не одной комбинации. Игрок может за один ход выложить 2-3 небольшие комбинации, которые вместе покрывают порог.

- FR-20: Пока команда не открыта, система ведёт **накопитель хода** — сумму очков всех новых (ещё не подтверждённых) комбинаций, выложенных в текущем ходу
- FR-21: Система не позволяет завершить ход сбросом карты, если команда не открыта и накопитель не достиг порога — сброс блокируется, пока условие не выполнено (или можно забрать карты обратно в руку)
- FR-22: Если ход завершается взятием сброса без покрытия порога — штраф 1000 (см. 3.5)

*(См. п.6 — как это выглядит в интерфейсе)*

### 3.4.1 Невозможность выполнить обязательное условие
- FR-22.1: Если игрок не может (физически нет подходящих карт) выложить обязательную комбинацию после взятия сброса, либо не может покрыть порог открытия — он может явно объявить это действием "не могу выложить" (единственная неизбежная кнопка в интерфейсе, вне логики drag & drop)
- FR-22.2: Действие "не могу выложить" применяет штраф −1000 очков команде и принудительно завершает ход обычным сбросом карты, без требования покрыть условие

### 3.5 Валидация правил (полностью на бэкенде)
- FR-23: Система проверяет ограничение "козырей не больше натуральных карт" в комбинации (кроме козырной канасты)
- FR-24: Система блокирует взятие сброса, если сверху тройка
- FR-25: Система блокирует докладывание в закрытую канасту (7 карт) и в чужие комбинации
- FR-26: Система применяет штраф 1000 очков за нарушения (взял сброс без выкладки / без покрытия порога)

### 3.6 Подсчёт и завершение
- FR-27: При выходе система автоматически считает очки сдачи по всем правилам (карты на руке/столе, бонусы, тройки, тип выхода)
- FR-28: Система прибавляет очки к общему счёту и запускает новую сдачу, если целевой счёт не достигнут
- FR-29: Система объявляет команду-победителя при достижении целевого счёта и показывает итоговую статистику партии
- FR-30: Игрок может увидеть историю прошедших сдач в рамках партии (кто сколько взял очков за сдачу)

### 3.7 Коммуникация
- FR-31: Игроки могут писать в общий текстовый чат комнаты (виден всем 4 игрокам, не только своей команде)
- FR-32: Система показывает лог последних игровых действий (кто что сделал) в виде ленты событий, отдельно от чата

## 4. Нефункциональные требования

- **NFR-1 (Realtime):** задержка отображения хода другого игрока — не более ~200-300 мс (WS, не polling)
- **NFR-2 (Устойчивость состояния):** обрыв соединения не должен ломать партию — состояние живёт в Redis независимо от коннекта
- **NFR-3 (Консистентность):** любое игровое действие валидируется только на сервере; клиент не может напрямую изменить состояние стола
- **NFR-4 (Конкурентность):** корректная обработка конкурентных действий — ход активен только у одного игрока за раз
- **NFR-5 (Масштаб):** расчёт на небольшую одновременную нагрузку (сотни, не тысячи комнат) — влияет на то, нужен ли шардинг WS сразу или хватит одного инстанса + Redis pub/sub
- **NFR-6 (UX/анимации):** переходы карт между зонами (рука → стол → сброс) анимируются плавно, без "скачков" состояния
- **NFR-7 (Отсутствие аккаунтов):** вход не требует пароля/почты — только имя и ссылка
- **NFR-8 (Персистентность истории):** результаты партий сохраняются в Postgres даже после выхода всех игроков из комнаты

## 5. Принцип взаимодействия с интерфейсом (design intent, не жёсткое требование)

Приоритет — минимизация отдельной панели кнопок, максимум действий через прямое взаимодействие с полем (drag & drop), там где это не мешает обязательности действия:

- Взятие карты из колоды — клик/тап по колоде (не drag, тут перетаскивать нечего)
- Взятие сброса — drag стопки сброса в руку, либо тап (тестируем оба варианта)
- Выкладка комбинации — drag карт из руки в зону стола / в существующий мельд
- Докладывание — drag карты на существующую стопку-мельд
- Кража козыря — drag нужной карты руки на козырь в чужом мельде
- Сброс карты — drag карты из руки в зону сброса

Кнопки оставляем только для действий без явного "места" на поле (подтверждение выхода, открытие истории сдач, чат). Это гипотеза интерфейса, будет тестироваться и может измениться после первых прототипов.

## 6. Как в интерфейсе показать прогресс к порогу открытия

Пока команда не открыта:
- У края стола (рядом со счётом команды) отображается **индикатор-полоска "прогресс открытия"**: `накоплено X / нужно Y`
- Индикатор обновляется **живо**, по мере того как игрок в текущем ходу перетаскивает карты в новые комбинации (до подтверждения хода)
- Если игрок пытается сбросить карту (завершить ход), а прогресс не достиг порога — сброс не срабатывает, поле подсвечивается, показывается объяснение ("нужно ещё N очков в комбинациях")
- После того как команда открылась — индикатор исчезает, дальше комбинации выкладываются свободно
- Технически: сервер хранит **накопитель хода** (turn accumulator) как часть turn state — сумма очков новых мельдов, созданных с начала текущего хода; сбрасывается в 0 в начале каждого нового хода

## 7. Turn state machine

Ход игрока проходит через фиксированные состояния:

1. **DRAW** — взятие карты (колода или сброс) → переход в ACT
2. **ACT** — выкладка/докладывание мельдов, кража козыря; можно повторять несколько раз за ход (несколько новых комбинаций подряд)
3. **DISCARD** — сброс карты, ход переходит к следующему игроку. Разрешён только если:
   - не активно требование "обязательный мельд после взятия сброса", ИЛИ оно уже выполнено
   - команда уже открыта, ИЛИ накопитель хода (см. 3.4) покрыл порог
4. **Переход ACT → DRAW следующего игрока** — если выкладка последней карты опустошила руку, но у команды нет закрытой канасты, ход завершается без сброса
5. **DEAL_END** — альтернативный выход из ACT: рука пуста и у команды есть закрытая канаста → чистый/грязный выход, подсчёт очков сдачи

**Edge case (важно поймать на этапе проектирования, не в проде):** если условие для DISCARD не выполнено, а у игрока физически нет карт, чтобы его выполнить, — состояние ACT становится тупиковым. Решение — явное действие **"не могу выложить"** (см. FR-22.1/22.2): применяет штраф 1000 и принудительно переводит в DISCARD без проверки условия. Это единственная кнопка в интерфейсе, которая не вписывается в философию drag & drop (раздел 5) — и осознанно.

## 8. WS-протокол клиент ↔ сервер

Принцип: клиент отправляет только **intent** (намерение), сервер — единственный источник истины, всегда отвечает полным персонализированным снепшотом состояния (не дельтами — партия небольшая, экономия не стоит риска рассинхрона). Анимации на фронте строятся поверх layoutId (Framer Motion) через сравнение предыдущего/нового state, отдельного протокола событий для анимации не требуется.

**Client → Server (intents):**
```
join_lobby          {name}
set_lobby_settings  {target_score, discard_visibility}     // host only
assign_seat         {player_id, seat}                      // host only
start_game          {}                                     // host only

draw_deck           {}
draw_discard        {}
create_meld         {card_ids: [...]}
add_to_meld         {card_ids: [...], meld_id}
steal_wild          {meld_id, wild_card_id, replacement_card_id}
discard             {card_id}
go_out              {final_card_id | final_meld_action}
concede_penalty     {}                                     // "не могу выложить"

send_chat           {text}
reconnect           {session_token}
```

**Server → Client:**
```
lobby_state         {players, seats, settings, host_id}
game_state          {hands (свои открыты, чужие — только count),
                      table melds по командам, deck_count, discard_pile,
                      scores, current_threshold, turn_player_id, turn_phase,
                      turn_accumulator}
action_error        {reason}          // ответ конкретному игроку на невалидный intent
deal_result         {scores_breakdown, next_deal | game_over}
game_over           {winner_team}
chat_message        {from, text, ts}
player_connection   {player_id, status: connected|disconnected}
```

Важно по безопасности: чужие руки **никогда** не приходят на клиент целиком — сервер шлёт каждому игроку персонализированный `game_state`, где видны только количество карт у остальных, а не их значения. Это закрывает читерство через devtools/network tab.

## 9. Схема данных движка (концептуально)

Чистые структуры, независимые от FastAPI/Postgres, живут в памяти/Redis на время партии. Совпадают по составу с `game_state` из WS-протокола (раздел 8) — один контракт на runtime-состояние и на wire-формат.

**Card:** id, rank (3–10/В/Д/К/Т/2/JOKER), suit (null для джокера), is_wild, point_value (вычисляется из rank)

**Meld** (комбинация на столе): id, team_id, kind (SET / SEQUENCE / WILD_CANASTA), rank_or_suit_anchor, slots (list[Card|null] — позиционный список для SEQUENCE, важно для кражи козыря), is_closed (7 карт), canasta_type (CLEAN/DIRTY/WILD, вычисляется при закрытии)

**TeamTable:** team_id, melds: list[Meld], is_opened, turn_accumulator (накопитель текущего хода к порогу, актуален пока !is_opened)

**TurnState:** current_player_id, phase (DRAW/ACT/DISCARD/DEAL_END), must_meld_after_pickup, pending_penalty (true после concede_penalty — следующий discard пропускает все проверки)

**DealState** (одна сдача): deck (list[Card]), discard_pile (list[Card], порядок важен), teams: dict[team_id, TeamTable], hands: dict[player_id, list[Card]], turn_state: TurnState, thresholds: dict[team_id, int] (фиксируются на всю сдачу)

**GameState** (вся партия): game_id, settings (target_score, discard_visibility), players (id/name/seat/team_id/session_token/connected), scores: dict[team_id, int], current_deal: DealState|null, deal_history: list[DealSummary]

## 10. Хранилище: Redis vs Postgres

Разделение: **Redis — то, что живёт, пока партия активна. Postgres — то, что должно пережить рестарт сервера и партию целиком.**

**Redis (ephemeral):**
- `game:{id}:state` → сериализованный GameState целиком (JSON), одна операция GET/SET на действие
- `game:{id}:lock` → мьютекс на время обработки одного action (защита от гонки при конкурентных интентах, NFR-4)
- pub/sub `game:{id}:events` → рассылка обновлений между WS-воркерами, если процессов несколько

**Postgres (персистентно):** таблицы `games`, `players`, `deals`, `chat_messages` — см. ER-диаграмму. `deal_events` (полный лог ходов для реплеев) сознательно вынесен за скобки MVP — nice-to-have, добавляется отдельно если понадобится фича "пересмотреть сдачу".

## 11. REST API (не-WS часть)

WS обслуживает игру целиком; REST — только вход в лобби до открытия сокета:
```
POST /games                  → создать игру (host), вернуть game_id + invite link + host_session_token
GET  /games/{id}/lobby       → инфо для стартовой загрузки страницы (до WS-коннекта)
POST /games/{id}/join        → войти по коду/ссылке, вернуть session_token
GET  /games/{id}/history     → история сдач (пост-игра/наблюдатель)
WS   /ws/games/{id}?token=…  → основной игровой канал
```

## 12. Структура backend-проекта

Движок изолирован от FastAPI и БД — чистый Python-модуль, тестируемый юнит-тестами без поднятия сервера:
```
app/
├── engine/              # чистая логика, без FastAPI/DB импортов
│   ├── models.py        # Card, Meld, TeamTable, TurnState, DealState
│   ├── rules.py         # валидация комбинаций, порогов, кражи козыря
│   └── turn_fsm.py      # машина состояний хода (раздел 7)
├── api/                 # REST-роутеры (lobby, join, history)
├── ws/                  # WS-хендлер, connection manager, роутинг intent → engine
├── db/                  # SQLAlchemy-модели + Alembic-миграции (зеркалят ER-диаграмму)
├── redis_store.py       # обёртка над Redis: get/set GameState, lock, pub/sub
└── schemas.py           # Pydantic-схемы — общий контракт для REST и WS сообщений

Dockerfile                # dev: hot-reload; Dockerfile.prod — слим multi-stage образ (шаг 31)
```

## 13. Frontend-структура

Стек: React + Zustand + Framer Motion (drag/layout-анимации). Компонентное дерево:

```
App
├── LobbyPage
│   ├── LobbyHeader        — invite-ссылка, кнопка "скопировать"
│   ├── SeatGrid            — 4 места, drag/клик для рассадки (только хост)
│   ├── LobbySettingsPanel  — целевой счёт, видимость сброса (только хост)
│   └── LobbyChat           — переиспользует ChatPanel
│
└── GamePage
    ├── GameHeader          — счёт команд, прогресс к target_score
    ├── Table
    │   ├── TeamZone (opponent, верх)
    │   │   └── MeldRow → MeldStack ×N
    │   ├── CenterArea
    │   │   ├── DeckPile     — клик = draw_deck
    │   │   └── DiscardPile  — top card или вся стопка (по настройке лобби), drop-зона для draw_discard
    │   ├── TeamZone (своя, низ)
    │   │   └── MeldRow → MeldStack ×N
    │   ├── ThresholdIndicator — плавающий, только пока команда не открыта (раздел 6)
    │   └── DragLayer        — оверлей поверх всего, рендерит перетаскиваемую карту
    ├── Hand                 — свои карты, draggable
    ├── OpponentHandBadge ×3 — количество карт у остальных (не значения — см. раздел 10 по безопасности)
    ├── TurnBanner           — "ваш ход" / "ходит Иван"
    ├── ConcedeButton        — "не могу выложить" (FR-22.1), видна только когда применимо
    ├── ChatPanel            — сворачиваемая боковая панель
    ├── EventLog             — сворачиваемая лента действий
    ├── DealResultModal      — разбивка очков после сдачи
    └── GameOverModal        — победитель + статистика партии
```

**MeldStack** — ключевой визуальный узел: верхняя карта + счётчик + цветная рамка по типу канасты; клик разворачивает **MeldDetailPopover** со всеми картами по слотам (нужно для кражи козыря — видеть, какую позицию в последовательности изображает козырь).

**DragLayer** — технический нюанс: `layoutId` из Framer Motion плохо анимирует переезд карты между разными поддеревьями DOM (Hand → Table, разные родители). Drag реализуется не через `layoutId`-репэрентинг, а через отдельный portal-компонент: во время перетаскивания исходная карта в Hand визуально гаснет, DragLayer рисует "призрак" карты, следующий за курсором; по отпусканию уходит intent на сервер; когда приходит новый `game_state`, целевой компонент (MeldStack) монтируется, и уже его появление анимируется через `layoutId` как "приземление".

## 14. Zustand-стор: слайсы

- **`useConnectionStore`** — WS-инстанс, статус соединения, session_token, состояние реконнекта
- **`useLobbyStore`** — данные лобби до старта партии (игроки, места, настройки, host_id)
- **`useGameStore`** — зеркало серверного `game_state` целиком. Принцип: **мутируется только обработчиком входящих WS-сообщений**, никогда напрямую компонентами — прямая реализация NFR-3 на фронте: клиент не изобретает состояние, только отображает присланное сервером
- **`useDragStore`** — эфемерный, НЕ синхронизируется с сервером: `activeDraggedCardId`, `hoveredDropZone`, `dragOrigin`. Сбрасывается на каждый жест. Поэтому `action_error` от сервера (невалидная выкладка) просто сбрасывает drag-стор, не трогая `useGameStore`, — карта "отскакивает" обратно, ничего не ломается
- **`useChatStore`** — сообщения, непрочитанные
- **`useUIStore`** — открытые модалки, id развёрнутого meld-попапа, состояние панелей

## 15. Реконнект: таймаут хода при дисконнекте активного игрока

Игра casual, с друзьями — карательные авто-действия при обрыве связи создают плохой опыт, поэтому логика намеренно мягкая:

- FR-33: Сервер фиксирует `player.connected = false` при закрытии WS-соединения и рассылает `player_connection` остальным игрокам
- FR-34: Если отключился игрок **не в свой ход** — партия продолжается как обычно, у его места отображается бейдж "офлайн"
- FR-35: Если отключился **ходящий** игрок (или очередь хода дошла до него, пока он offline) — сервер запускает таймер хода (по умолчанию 90 сек, настраиваемо), остальные видят обратный отсчёт
- FR-36: Реконнект в течение таймера — по `session_token` сервер узнаёт место игрока, присылает полный снепшот на **той же фазе turn_state**, на которой игрок вышел (DRAW/ACT/DISCARD); таймер отменяется, игрок доигрывает без потери прогресса хода
- FR-37: По истечении таймера система **не форсит случайный ход**. Партия ставится на паузу для этого хода; у хоста появляется ручная кнопка "пропустить ход с штрафом" — осознанное административное действие (не drag & drop, не автоматика). Применяет штраф 1000 (аналогично `concede_penalty`), карты игрока остаются у него на руке (не сбрасываются), ход переходит следующему
- Без таймаута по умолчанию игра может просто ждать сколь угодно — таймер это защита от сценария "человек ушёл насовсем", а не попытка форсировать скорость игры

## 16. Use-case'ы (сценарии)

**UC-1: Создание и старт партии**
Актор: Хост
1. Хост вводит имя, задаёт настройки (целевой счёт, видимость сброса), жмёт "Создать игру"
2. Система создаёт комнату, показывает ссылку-приглашение
3. Хост делится ссылкой с 3 друзьями
4. Друзья заходят по ссылке, вводят имена, попадают в лобби
5. Хост распределяет по местам (или автоматически по порядку входа)
6. Хост жмёт "Начать" — система раздаёт карты, запускает первую сдачу

**UC-2: Выполнение хода**
Актор: Игрок, чья очередь
1. Игрок видит подсветку "ваш ход", остальные видят "ходит Х"
2. Игрок берёт карту из колоды или сброс
3. (если сброс) система требует выложить комбинацию
4. Игрок опционально выкладывает/докладывает карты; если команда не открыта — видит индикатор прогресса (п.6)
5. Игрок сбрасывает карту
6. Ход переходит следующему по кругу

**UC-3: Кража козыря**
Актор: Игрок в свой ход
1. Игрок видит козырь в открытом мельде противника
2. Перетаскивает нужную карту из руки на этот козырь
3. Система проверяет соответствие карты позиции/номиналу, меняет местами
4. Козырь уходит в руку игрока, доступен для использования в этом же ходу

**UC-4: Выход и подсчёт сдачи**
Актор: Игрок, завершающий сдачу
1. У команды есть минимум одна завершённая канаста
2. Игрок выкладывает/докладывает последнюю карту руки
3. Система фиксирует тип выхода (чистый/грязный), считает очки обеих команд
4. Экран показывает разбивку очков сдачи, обновляет общий счёт
5. Если целевой счёт не достигнут — старт новой сдачи; иначе — экран победителя

**UC-5: Реконнект**
Актор: Игрок, потерявший соединение
1. Игрок закрывает вкладку / теряет сеть посреди партии
2. Партия продолжается для остальных (или ожидает, если сейчас его ход — с таймаутом, TBD)
3. Игрок открывает ссылку снова — по токену сессии система узнаёт его место
4. Клиент получает полный снепшот текущего состояния, доигрывает

## 18. Технические договорённости перед стартом

- **Репозиторий:** монорепо, один git-репозиторий, `/backend` и `/frontend` рядом в корне — проще для одного разработчика с Claude Code, не нужно синхронизировать версии между репами
- **Backend:** Python 3.12, менеджер пакетов `uv`, тесты — `pytest`, линтер/форматтер — `ruff`
- **Frontend:** Node LTS, менеджер пакетов `pnpm`, тесты — `Vitest`, линтер — `eslint` + `prettier`
- **Конфигурация:** `.env.example` заводится в шаге 1 (не в 31) — `DATABASE_URL`, `REDIS_URL`, `CORS_ORIGINS`, `SECRET_KEY` (для session_token). Backend читает конфиг через `pydantic-settings`
- **CORS:** в dev-режиме backend разрешает origin фронтенда (`http://localhost:5173` по умолчанию для Vite) — иначе первый же WS/fetch с фронта на бэк упадёт
- **session_token:** непрозрачный случайный токен (`secrets.token_urlsafe`), не JWT — не нужна проверка подписи на клиенте, только сервер знает валидность
